# mobile-qa e2e

Твоя работа здесь: поднять окружение правильно, прогнать Maestro-флоу и
честно пересказать, что он вернул. Сам ничего не измеряй и не досочиняй —
измеряет Maestro, а не ты.

## Одна обязанность: находить и объяснять, не чинить

Это не опциональная вежливость, а граница ответственности (single
responsibility — у этого скила одна работа, не две). Что бы ни нашёл
прогон или твой собственный разбор по коду (см. «Судья» ниже) —
**ты не правишь код приложения**. Даже если причина очевидна и фикс в одну
строку (как `onMount`-валидатор, которого не хватает в форме логина). Твоя
находка заканчивается на подробном отчёте: что сломано, почему (с
указанием файла и строки), что сделать и какой ценой. Делать это —
решение человека и чужая зона ответственности (тот, кто ведёт экраны и
код). `allowed-tools` этого скила (`Bash, Read, Glob, Grep`) не просто
список — в нём намеренно нет `Edit`/`Write`: это не формальность, а то же
самое ограничение, закреплённое инструментально, не только словами.

## Каждый тест объясняет сам себя

Флоу не должен быть только последовательностью `tapOn`/`assertVisible` —
тому, кто его читает (включая тебя через полгода), должно быть сразу
понятно, зачем он существует, а не только что он делает. Перед `---` в
каждом `.yaml`-флоу — короткий блок:

```yaml
# Цель: <что тест защищает / какой регресс или риск предотвращает>
# Контекст: <почему это важно — находка/инцидент, если был, иначе пусто>
```

Пример из реального найденного случая: тест проверяет не "кнопка
disabled", а "пользователь не может отправить запрос в API с заведомо
невалидными данными, потому что клиент даже не попытался их
провалидировать до отправки" — вот это и есть цель, а
`assertVisible enabled: false` — только механика, которой эта цель
достигается. Та же логика относится к `TEST_PLAN.md` целевого проекта,
если он есть: колонка "Ожидаемый результат" — место для цели, не только
для шагов.

## Новая машина / первый раз в этом проекте — сначала doctor

Если не уверен, что на машине вообще стоит Maestro/Xcode/симулятор/
`node_modules`, или `ensure-env.sh` уже упал кодом 3 — не чини по одной
детали методом тыка, сразу посмотри целиком:

```bash
.claude/skills/mobile-qa/scripts/doctor.sh
```

Ничего не устанавливает сам, только читает и печатает рецепт на каждую
недостающую часть — включая реальный инцидент из этой же сессии (`brew
install maestro` без `--formula` подхватывает **чужой** каск с тем же
именем, не тот Maestro). Каждая находка помечена, кто её чинит:

- **`[агент может починить с согласия]`** — Maestro, node, `pnpm install`,
  `.maestro/config.json` (его можно собрать самому: прочитать bundle
  id/scheme из `app.config.ts`/`app.json` проекта). Предложи рецепт
  человеку в чате, и только после явного «да» выполни его `Bash` —
  ровно так ставился Maestro в начале этой сессии. Не предлагай все
  четыре разом одним сообщением; чини по одной, перезапускай `doctor.sh`
  после каждой, прежде чем переходить к следующей — порядок важен
  (без Homebrew не поставить Maestro).
- **`[только вручную]`** — Homebrew, Xcode Command Line Tools, рантайм
  iOS-симулятора. Это либо системный GUI-диалог (пароль, лицензия), либо
  многогигабайтная загрузка с согласием в самом Xcode — агент физически
  не пройдёт это даже с согласия человека. Объясни, что нужно сделать, и
  остановись: не пытайся найти обходной путь через `curl`/`defaults
  write`/автоматизацию GUI.

## Порядок, который нельзя менять

**1. Сначала самопроверка.** Без неё по-настоящему новый прогон не запускай:

```bash
.claude/skills/mobile-qa/scripts/selftest.sh
```

Сначала сама поднимает окружение (`ensure-env.sh`), потом гоняет
канонический набор `.maestro/` — ровно ту команду, что зафиксирована в
`.maestro/TEST_PLAN.md`: `maestro test .maestro --exclude-tags
destructive,needs-fixture,subflow`. Если окружение не поднялось вовсе —
код **3**. Если окружение было готово, но хоть один флоу всё равно не
прошёл — код **2** и автоматически пишутся отчёты в `.maestro/reports/`
(см. раздел «Отчёты о находках» ниже). Код 2 значит «что-то не так в
флоу/приложении при готовом окружении», не путай с кодом 3.

**2. Конвенцию testID не выдумывай.** Она живёт в `CLAUDE.md` корня проекта
(раздел «Конвенция testID») — прочитай его перед тем, как писать новый флоу
или угадывать селектор. Элемент без `testID` — не повод бить по тексту или
координате; это отдельная находка «нет testID», которую нужно явно назвать,
а не обойти.

**3. Прогон.** Экран/флоу, который просит человек, запускается через

```bash
.claude/skills/mobile-qa/scripts/run.sh <путь-к-flow.yaml> [--include-destructive]
```

Коды возврата: `0` чисто, `1` флоу упал на реальном шаге, `2` самопроверка
провалена, `3` не удалось запустить вовсе.

## Окружение — проект-специфичное живёт в конфиге, не в скиле

Этот скил рассчитан на Expo + iOS Simulator — так проверено на этом
проекте. На другом стеке (bare RN, Android-first, Flutter, нативный iOS
без Expo) ниже описанное **не переносится буквально**: переоткрой то же
самое для своего стека (deep link может не существовать вовсе, служебных
оверлеев может не быть, Keychain-поведение — только iOS), не копируй шаги
вслепую только потому, что они сработали здесь.

- `appId` и схема deep link к dev client — **не хардкодь в скиле**, читай
  из `.maestro/config.json` целевого проекта (`appId`, `devClientScheme`,
  опционально `metroPort`). Это не секрет, в отличие от `.maestro/.env` —
  коммитится в репозиторий. `ensure-env.sh` сам останавливается кодом 3,
  если файла нет, вместо того чтобы угадать или унаследовать значение из
  другого проекта.
- Окружение (симулятор + Metro) поднимает `scripts/ensure-env.sh` сам —
  не выясняй вручную, не проси человека забутить симулятор заранее.
  Первый запуск: первый доступный iPhone-симулятор (не реальное
  устройство — `xcrun simctl` физические девайсы в принципе не видит),
  UDID фиксируется в `.maestro/.device` и переиспользуется дальше, а не
  выбирается заново каждый раз. Metro стартует в фоне (детач, PID в
  `.maestro/.metro.pid`) и переживает несколько вызовов подряд. Если
  приложение не установлено на симуляторе — скил не билдит сам (дорогая
  операция), а честно останавливается кодом 3 с инструкцией. Если на
  машине вообще нет Maestro или Xcode-симулятора — та же честная остановка
  кодом 3, не тихий пропуск.
- Dev client (Expo) не подхватывает Metro заново сам по себе: первый шаг
  флоу — `openLink` на `<devClientScheme>://expo-development-client/?url=...`
  сразу после `launchApp`, иначе приложение застревает на экране выбора
  сервера разработки. Схему бери из `.maestro/config.json`, не из примера
  ниже: `exp+<slug>` — это схема конкретного приложения, у твоего она своя.
- Dev client поверх этого добавляет два служебных слоя, которых **нет** в
  preview/production сборке: онбординг-тултип «Continue» (кнопка открытия
  меню разработчика) и системный диалог запроса на push-уведомления. Они
  могут появиться в любом порядке на холодном старте и перекрыть экран
  приложения. Гасить условно, не считать находкой:
  ```yaml
  - runFlow:
      when:
        visible: "Continue"
      commands:
        - tapOn: "Continue"
  - runFlow:
      when:
        visible: "Не разрешать|Don.t Allow"
      commands:
        - tapOn: "Не разрешать|Don.t Allow"
  ```
  Ставь оба блока **дважды** подряд (один диалог иногда открывает место для
  второго) — так сделано в `login-logout.yaml`, копируй паттерн оттуда, а не
  изобретай заново.
- **Keychain переживает `clearState: true`** на iOS (так и задумано в iOS, не
  баг). Флоу, которому нужен разлогиненный старт, не может полагаться на
  `clearState` — вместо этого он сам проверяет, не на таб-баре ли уже
  (`when: visible: ".*tab, 1 of 5"`), и если да — логаутится первым шагом.
  Делает флоу идемпотентным: можно гонять подряд с любого состояния.
- **Элемент с `opacity: 0` / нулевым размером выпадает из accessibility-
  дерева iOS целиком**, не просто помечается невидимым. Maestro не видит
  такой элемент вообще. Если дизайн использует скрытый `TextInput` для
  управления видимыми ячейками рядом (как OTP-поле в этом проекте), `testID`
  должен стоять на видимом родителе (`Pressable`/`View`), который фокусирует
  скрытый инпут по тапу, а не на самом скрытом элементе.
- **Локаль интерфейса — на аккаунте, не на симуляторе.** В этом проекте язык
  UI переключается пользователем в настройках и хранится на бэкенде, поэтому
  один и тот же симулятор может показать то "Welcome, …", то "Добро
  пожаловать, …" в зависимости от того, под каким аккаунтом зашли. Не матчи
  видимый текст напрямую, где можно matched локаль-независимый паттерн:
  системный accessibility-суффикс таб-бара `"tab, N of 5"` **не
  переводится**, в отличие от подписи таба — используй `text: ".*tab, N of 5"`
  вместо `text: "Profile, tab, 5 of 5"`.
- **Правишь bash-скрипты скила — не пиши `producer | grep -q ...` или
  `producer | head -N ...` напрямую** под `set -o pipefail` (он стоит во
  всех скриптах скила). `grep -q`/`head -N` выходят раньше, чем producer
  дописал вывод, producer получает SIGPIPE и возвращает ненулевой код,
  `pipefail` считает весь пайплайн упавшим — даже если консьюмер реально
  нашёл то, что искал. Поймано на практике в `ensure-env.sh`: проверка
  установленного приложения падала через раз именно так. Паттерн:
  `VAR="$(producer)"`, потом парсить `$VAR`.

## OTP-обход (тестовый вход)

Тестовый номер и код лежат в `.maestro/.env` проекта (в `.gitignore`, вне
скила и вне кода). Скил передаёт их через `-e` флаги Maestro:

```bash
source .maestro/.env
maestro --udid <udid> test <flow>.yaml \
  -e TEST_PHONE_NATIONAL="$TEST_PHONE_NATIONAL" -e TEST_OTP="$TEST_OTP"
```

**Никогда** не хардкодь эти значения в `.yaml`-флоу или в самом скиле, и не
спрашивай их у человека в чате — файл либо уже есть, либо прогон логина
невозможен, и это стоит сказать прямо, а не придумывать значения.

## Guardrail на запись — стейджинга нет

У проекта нет тестового окружения (см. `docs/ARCHITECTURE.md` /
`.env.development`): любой флоу бьёт по реальному бэкенду. Полный каталог
тестов по каждому из 18 экранов с пометкой риска — `.maestro/TEST_PLAN.md`
корня проекта, источник правды, не дублируй его здесь. Три тега, не два:

- `destructive` — меняет реальные данные на проде (регистрация, выбор
  программы, смена профиля). В обычный прогон не входит никогда без
  явного флага.
- `needs-fixture` — нужен аккаунт в конкретном состоянии (пустые списки,
  403, контракт без `canSign`), которого в репозитории нет. Флоу написан,
  но по дизайну не считается зелёным без фикстуры — не притворяйся, что
  он часть самопроверки.
- `subflow` — переиспользуемый кусок (`subflows/launch-dev-client.yaml` и
  похожие), не самостоятельный тест, не должен запускаться как отдельный
  флоу верхнего уровня.

Канонический прогон (см. `.maestro/TEST_PLAN.md`):

```bash
maestro test .maestro --exclude-tags destructive,needs-fixture,subflow
```

`selftest.sh` и `run.sh` используют её же — не выдумывай свой набор
тегов отдельно. `run.sh <flow> --include-destructive` снимает исключение
для одного целевого `destructive`-флоу — это осознанный выбор того, кто
запускает, а не скила.

## Отчёты о находках

`selftest.sh`/`run.sh` при падении сами зовут

```bash
.claude/skills/mobile-qa/scripts/report.sh <junit.xml> [maestro-debug-dir]
```

и пишут по одному файлу на упавший флоу (или на группу флоу — см. ниже):
`.maestro/reports/<дата>-<флоу>.md` + скопированный рядом скриншот места
падения (не ссылка на `~/.maestro/tests/` — та папка живёт вне проекта и
может быть вычищена). Отчёты коммитятся в репозиторий — это история
найденных багов, а не мусор; скриншоты внутри растят репо, но это
документальность, а не шум.

### Один баг — один отчёт, не один отчёт на экран

Переиспользуемый компонент (модалка, карточка, строка списка) один раз
сломан — и ломается одинаково на каждом экране, где используется. Без
дедупликации это выглядит как N багов вместо одного, и отчёт перестаёт
быть полезным: человек читает пять почти одинаковых файлов вместо одного
с полным разбором причины. Два уровня, не путай:

- **Точное совпадение текста ошибки в одном прогоне** — это уже делает
  сам `report.sh` механически: если несколько флоу в одном JUnit упали на
  буквально одинаковом сообщении Maestro, пишется один файл
  `<дата>-<первый-флоу>-and-N-more.md` со списком всех затронутых флоу и
  скриншотом от каждого. Скрипту для этого не нужно понимать код — только
  сравнить строки.
- **Разные сообщения, одна причина в коде** — это механически не
  решается, и это твоя работа, не скрипта. Два флоу могут упасть на
  разных селекторах на разных экранах, но причина — один и тот же баг в
  одном переиспользуемом компоненте. Прежде чем писать новый отчёт как
  отдельную находку: `grep` по `.maestro/reports/*.md` на имя компонента,
  который ты уже процитировал в чужом вердикте. Нашёл совпадение — не
  дублируй полный разбор, допиши в существующий отчёт строку «Также видно
  в: `<флоу>`, причина та же (см. выше)» вместо нового файла с повторным
  Решение/Почему/Что сделать.

Читая отчёт (или сырой вывод Maestro, если `report.sh` почему-то не
вызвался), пересказывай честно:

- какой именно шаг упал — имя команды и селектор из `<failure>`, не
  "что-то не работает";
- открой скопированный скриншот (`Read`) и опиши, что реально на экране,
  а не предполагай причину по одному тексту ошибки;
- если причина — служебный диалог/оверлей dev client (см. раздел про
  окружение выше), это находка про окружение, а не про приложение — так и
  скажи, и не создавай отдельный баг-репорт на это;
- если скриншот показывает реальное поведение приложения, отличное от
  ожидаемого в `.maestro/TEST_PLAN.md` — это находка о приложении. **Ты сам
  и есть главный судья** (см. ниже, почему `judge.py` — не то же самое):
  прочитай релевантный экран/компонент (`Read`/`Grep` по testID или
  селектору из сообщения Maestro) и подтверди или опровергни находку по
  исходнику, а не по одному скриншоту. Допиши вердикт прямо в
  `.maestro/reports/<файл>.md` в том же формате: Решение
  (подтверждаю/ложная/мало данных) / Почему / Что сделать, со ссылкой на
  конкретную строку кода — так дешевле и надёжнее, чем гадать по тексту
  ошибки.

**Задачи в трекер скил пока не заводит** — это осознанно отложено
(обсуждалось с человеком: "в будущем продумаем, как сделать так, чтобы
сам создавал задачи"). Текущая граница — зафиксировать находку в
`.maestro/reports/`, а не придумывать несуществующую интеграцию с
трекером.

## Судья: ты сам (с кодом) vs `judge.py` (без кода) — не путать

Падение Maestro-шага не всегда значит баг в приложении: может быть флейк
окружения (сеть, таймаут анимации, гонка диалогов). Есть два судьи, и они
не взаимозаменяемы:

1. **Ты, агент, который ведёт эту сессию.** У тебя уже есть `Read`/`Grep`/
   `Bash` — те же инструменты, что у человека-разработчика. Это твой
   основной путь: смотришь на упавший селектор/testID, грепаешь нужный
   экран или компонент, читаешь реальную логику (валидацию, условие
   рендера, обработчик) и выносишь вердикт **по коду**, не только по
   скриншоту. Так был разобран реальный случай 2026-10-20: падение
   `login-form-submit` выглядело как "кнопка не задизейблена" по
   скриншоту, но подтвердилось только после чтения `form.Field`-валидатора
   в исходнике — без этого было бы просто "мало данных".
2. **`judge.py`/`judge.sh`** — узкий автоматический fallback для случаев
   **без** живого агента (расписанный прогон в CI, где скил стоит, а
   Claude Code рядом не запущен). Намеренно **не видит код, репозиторий
   или сеть** — только текст находки и, если доступен, скриншот, через
   внешний OpenAI-совместимый API. Это осознанное ограничение из
   `qa-audit`: не отправлять исходный код проекта в чужой внешний сервис
   по чужому ключу. `report.sh` зовёт его автоматически, если заданы
   **обе** `MOBILE_QA_JUDGE_URL` и `MOBILE_QA_JUDGE_KEY` (одного ключа без
   адреса недостаточно — пропустится молча с причиной "не заданы", не
   ошибкой), но его вердикт всегда слабее твоего собственного разбора по
   коду — не полагайся на него, если можешь прочитать источник сам. Вызов
   вручную для одной находки:

```bash
.claude/skills/mobile-qa/scripts/judge.sh "<находка одной строкой>" "<путь к скриншоту, если есть>"
```

Три переменные окружения, не аргументы команды и не чат: `MOBILE_QA_JUDGE_URL`
(адрес OpenAI-совместимого API), `MOBILE_QA_JUDGE_KEY` (ключ), опционально
`MOBILE_QA_JUDGE_MODEL`. Нет `URL`/`KEY` — судья пропускается молча,
результат всё равно отдаётся, просто без разбора; это не повод остановить
прогон. Полный свод правил судьи — `rules/judge-rules.md`, читай перед
первым вызовом.
